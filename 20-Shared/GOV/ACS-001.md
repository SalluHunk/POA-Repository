# A. Purpose

`ACS-001` establishes Certification as a formally defined governed-review status tier for POA artifacts, distinct from — and reachable only after — Approved or Accepted status.

Prior to this standard, "Certified" appeared in repository practice only as an undefined, informal peer of "Approved"/"Accepted" (`POA-INTEGRITY-CONTROL-001`'s own status field; the `RSR-001` report instance's inclusion rule), and as a named-but-never-defined concept (`GAP-003`; `POA-MAT-001` §7; `ADR-RM-001` §6). No prior document stated what distinguished Certified from Approved, Accepted, or Complete. This standard closes that specific, narrow gap. It does not, by its own existence, certify any artifact (§T).

---

# B. Scope

This standard's primary, evidenced scope is **artifact-level certification**: any repository artifact carrying its own Identity-block Status field is eligible to be evaluated for certification under this standard.

A second, thinly evidenced class — **Mission Package certification** — was once named as proposed scope (`ADR-RM-001` §7: "Architectural Certification Record (`ACS-001` footer)") but was never implemented in `POA-STD-011` itself. This standard names Mission Package certification as a recognized future extension of this same vocabulary and lifecycle, without fully specifying its mechanics now — doing so on the available evidence would exceed what is groundable (`40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §C).

**Out of scope:** capability-level certification (capability status is derived from its introducing artifact's own status, per `POA-RSR-001` §6 — no independent object to certify) and baseline-level certification (`GAP-006` — no baseline artifact exists at any version to certify).

---

# C. Certification Vocabulary

The following terms are **newly defined by this standard.** None was established by any prior repository artifact; each closes a gap identified in `40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §B.1/§B.11.

- **Certified** — an artifact's Status field value indicating it has passed a review meeting this standard's evidence and authority requirements (§G, §I), in addition to (not instead of) already holding Approved or Accepted status.
- **Certification Record** — the artifact's own Status field, updated to read "Certified," together with a citation to the reviewing authority's decision and the evidence considered (§J). No separate record type is created.
- **Certification Class** — the category of object certification attaches to (§D).
- **Certification Eligibility** — the preconditions an artifact must meet before certification review may begin (§E).

---

# D. Certification Classes

1. **Artifact Certification** (primary, defined class) — applies to any repository artifact with its own Status field.
2. **Mission Package Certification** (named, not yet specified) — recognized as a future extension per §B; `RESERVED / GOVERNANCE DEPENDENCY` for its full mechanics (eligibility, evidence, authority) until a dedicated future mission grounds it in implemented `POA-STD-011` practice rather than the currently unimplemented `ADR-RM-001` §7 proposal. **Reviewed under `GOV-003` and deliberately left unresolved:** the Commander ruling names "certification decisions" generally but does not mention Mission Packages; nothing in it legitimately supports resolving this class's mechanics now.

No other certification class is established or invented.

---

# E. Eligibility

An artifact is eligible for certification review only if:

1. It already holds **Approved** or **Accepted** status (its own literal Status field) — certification is a tier reached *after* approval/acceptance, never a substitute path to reach the same place a faster way.
2. It is not `POA-STD-011` or any other artifact this mission is expressly forbidden from certifying or promoting (§T).
3. No open, unresolved governance conflict names it directly (e.g., an artifact caught in a HELD gap such as `GAP-001` is not eligible while the conflict remains HELD).

This eligibility rule is authored new by this standard; no prior artifact stated it. See `40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §C row E.

---

# F. Preconditions

Beyond eligibility (§E), before a certification review may begin:

1. The artifact's current Status field and Version must be stable (not mid-revision) at the time review is requested.
2. The proposer (§H) must identify the specific evidence (§G) they assert satisfies this standard.

No prior artifact defines certification preconditions; this section is authored new, extending §E.

---

# G. Required Evidence

Certification review requires evidence addressing, at minimum, the same categories already used elsewhere in this repository to establish an artifact is genuinely complete and sound — reused by analogy, not previously certification-specific:

- Analogous to `POA-MAT-001` §6 (Definition of Done): the artifact is materialized, satisfies its own naming convention, is correctly placed, and introduces no undisclosed architectural deviation.
- Analogous to `POA-EXB-001` §11 (Success Criteria): the artifact can be independently exercised or reviewed without requiring conversational context not captured in the artifact itself.
- Traceability evidence per `CLAUDE.md` Rule 6: which mission authorized it, which source artifact it derives from, which commit introduced it.
- A statement of the artifact's own current Approved/Accepted status and the record establishing it (§E.1).

This is a starting evidence baseline drawn from existing repository analogues, not a rediscovery of pre-existing certification-specific criteria — none exist (`40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §B.10).

# H. Review Process

**Reviewer identity RESOLVED (`GOV-003`):** the certification reviewer is the **Chief Navigator & Architecture Steward** — operationally titled "Chief Architect" per `ORC-001-GOV-001`'s GOV-003 Addendum §1 — exercising the certification authority delegated in that same Addendum §2.

1. The proposer (§I) identifies an eligible artifact and the evidence (§G) supporting certification.
2. The Chief Navigator & Architecture Steward reviews the artifact against §E–§G.
3. The Steward records a decision: grant, decline, or hold for further evidence — subject at all times to Commander's reserve/escalate/override/withhold/revoke supremacy (`ORC-001-GOV-001` GOV-003 Addendum §3; §I below).
4. If granted, the artifact's own Status field is updated to "Certified," with a citation to this review (§J, §R).

**Procedural mechanics remain RESERVED / GOVERNANCE DEPENDENCY:** the Commander decision resolves *who* reviews, not the operational detail of how a review request is submitted, tracked, or timed. Not invented here.

---

# I. Authority / Decision Rights

**Who may propose certification — RESOLVED, narrowly (`GOV-003`):** the Chief Navigator & Architecture Steward, holding certification authority in full (`ORC-001-GOV-001` GOV-003 Addendum §2), may propose and initiate a certification review on its own initiative. **This is the reading `GOV-003` adopted, stated so it can be rejected in one line if wrong:** the Commander decision grants "certification authority" as an undivided whole, and the power to decide is read here as including the power to open the question in the first place. **Whether any other actor (e.g., a Repository Materializer, Mission Control) may also submit a candidate for the Steward's review is RESERVED / GOVERNANCE DEPENDENCY** — the Commander ruling does not address third-party proposal rights, and none is invented here.

**Who may approve/grant certification — RESOLVED (`GOV-003`):** the **Chief Navigator & Architecture Steward**, per `ORC-001-GOV-001`'s GOV-003 Addendum §2 ("Certification authority... is delegated to the Chief Navigator & Architecture Steward"). This supersedes this section's prior reasoned-analogy answer (Commander, by inference) — the actual Commander ruling delegates to the Steward, not to Commander directly, subject always to Commander's retained supremacy (§ below).

**Whether "Chief Architect" authority alone is sufficient — RESOLVED (`GOV-003`):** yes, because "Chief Architect" and "Chief Navigator & Architecture Steward" are the same role under different names (`ORC-001-GOV-001` GOV-003 Addendum §1) — there is no second, lesser authority being asked to act "alone." Acting as "Chief Architect" on a certification matter *is* the Steward exercising its delegated certification authority.

**Commander supremacy over certification (`ORC-001-GOV-001` GOV-003 Addendum §3):** notwithstanding the delegation above, the Commander may at any time reserve a certification decision to itself, escalate a pending review, override a Steward decision, withhold certification despite a Steward recommendation, or revoke a certification the Steward has granted. This is the check on the delegation above; the underlying procedural mechanics remain RESERVED (§H).

**Self-review boundary — named, not resolved:** the certification reviewer and the certifying/granting authority now both resolve to the same role (the Steward, operationally "Chief Architect") — the same actor who also grants "Chief Architect acceptance" on the missions producing candidate artifacts in the first place. Commander supremacy is the stated check on this; the Commander ruling does not otherwise address self-review. Named here as an open structural question, not solved by this mission.

**Explicit self-certification bar:** `ACS-001` cannot certify itself, and no artifact created in the same mission that materializes or amends this standard may be certified as a side effect of that materialization (§T).

# J. Certification Record Requirements

A certification record is not a new document type. It is:

1. The certified artifact's own Identity-block Status field, updated in place to "Certified" (or "Certified — [qualifier]" where a qualifier is needed), per the existing universal repository convention already used for every Status field read during Phase 1 (`40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §B.13).
2. An inline citation within that same field or its surrounding text, naming: the certifying authority (**RESOLVED, `GOV-003`: the Chief Navigator & Architecture Steward, citing `ORC-001-GOV-001`'s GOV-003 Addendum §2 as its delegated basis**), the date, and the evidence considered (§G).
3. Where Commander exercises reserve/escalate/override/withhold/revoke (§I), that intervention is recorded the same way — additively, dated, citing `ORC-001-GOV-001`'s GOV-003 Addendum §3 — and is never merged into the Steward's own grant record as if the Steward had made the same decision.

No separate certification-record artifact type is invented.

---

# K. Certification Lifecycle

Certification extends the existing repository-wide lifecycle already cited by `POA-META-001` (per `REPO-AUTHORITY-RECONCILIATION-REPORT.md` §2):

```text
Proposed → Draft → Review → Approved → Active → Revised → Superseded → Archived
```

This standard inserts an optional additional stage, reachable only after Approved (or, per this repository's own Accepted-status practice, after Accepted):

```text
... → Approved / Accepted → [Certification Review] → Certified → ... → Revised / Superseded → Archived
```

Certified is a status an artifact may carry in addition to having passed through Approved/Accepted — it is not a replacement stage and does not skip Approved/Accepted.

---

# L. Revocation / Supersession

Certification may be revoked or superseded using the same "Revised"/"Superseded" mechanics already present in the lifecycle above (§K) — extended by analogy, not invented from nothing (`40-Runtime/GOV-001-PREFLIGHT-REPORT.md` §B.12). **Who may revoke — RESOLVED (`GOV-003`):** either (a) the granting authority (the Chief Navigator & Architecture Steward) using ordinary lifecycle revision, or (b) the Commander, at any time, exercising the supremacy expressly granted in `ORC-001-GOV-001`'s GOV-003 Addendum §3 — both grounded directly in the Commander ruling, neither invented. A revocation:

1. Must be objectively evidenced (per the Control Law pattern already established in `POA-INTEGRITY-CONTROL-001`).
2. Must be performed by (a) or (b) above.
3. Must be recorded additively (the certification grant's own historical record is not deleted; a dated revocation entry is appended, citing which of (a)/(b) performed it), consistent with `POA-INTEGRITY-CONTROL-001` §L (Historical Integrity Rules).

---

# M. Relationship to Acceptance and Approval

**This is the standard's most load-bearing rule, and it is stated exactly as the authorizing directive requires:**

Certification MUST NOT be inferred from:

- implementation completion,
- acceptance alone,
- approval alone,
- repository presence,
- Commander authorization alone,
- or self-declaration,

unless this standard's own eligibility (§E), evidence (§G), and authority (§I) requirements have been explicitly satisfied and recorded (§J). An artifact holding Approved or Accepted status is *eligible* for certification review (§E.1) — it is not thereby *certified*. The two are always distinct, and the gap between them is never closed automatically.

# N. Relationship to RSR

`20-Shared/RSR/POA-RSR-001.md` — the Repository State Report specification — **does not use the word "certification" anywhere in its own text.** The term entered practice only through the `40-Runtime/RSR-001-REPOSITORY-STATE-REPORT.md` *instance's* Chief-Architect-directed correction, which treated "Approved / Accepted / Certified" as a peer group qualifying an artifact for §4 Artifact Inventory inclusion, without ever defining what "Certified" meant.

`ACS-001` now supplies that definition prospectively. This is `ACS-001` establishing the relationship for the first time, not recovering one that already existed in the specification. Future RSR instances applying `POA-RSR-001`'s literal-status inclusion rule may now treat "Certified" as this standard defines it; `POA-RSR-001` itself is not modified by this standard.

---

# O. Relationship to Integrity Control

`40-Runtime/POA-INTEGRITY-CONTROL-001.md` already treats certification-tier status changes as reserved to a dedicated governance mission: its own status field distinguishes "Materialized" from "Approved/Accepted/Certified," and its Integrity Dimension 6 ("Governance state") requires that standard-artifact statuses "remain what they were before the cycle, unless a dedicated governance mission changed them."

`ACS-001` confirms and formalizes this existing rule rather than changing it: a routine integrity cycle (`POA-INTEGRITY-CONTROL-001` §G/§H) may never itself grant, revoke, or alter a Certified status — only a dedicated certification review under this standard (§H, §I) may do so.

# Q. Exceptions / Waivers

Mostly **RESERVED / GOVERNANCE DEPENDENCY.** The only evidenced analogue is `20-Shared/DECISIONS/ADR-002-Sprint-Alpha-Gap-Waiver.md`, a Commander-issued decision authorizing scoped work to proceed despite open governance gaps. It is recorded here only as the repository's one existing precedent for how a Commander-level exception to a governance constraint is documented (a scoped, dated ADR), should a future certification exception ever be needed. **Reviewed under `GOV-003` and deliberately left unresolved:** the Commander ruling does not establish an exception/waiver mechanism specific to certification; nothing legitimately supports defining one now.

# R. Historical Integrity Requirements

Certification actions (grants, declines, holds, revocations) follow the same historical-integrity discipline already established by `POA-INTEGRITY-CONTROL-001` §L:

- A certified (or previously certified) artifact's own historical narrative sections are never rewritten by a certification action.
- A certification action touches only the artifact's own Status field (an identity/status field designed to be current) or appends a dated, additive record — never both merged into one edit.
- Every certification action records what changed, its authoritative basis, and does not fabricate a stronger evidentiary basis than actually exists (e.g., does not present an in-session confirmation as a dated external record where none exists — the same distinction `SR-001` and `INT-001` already preserve for acceptance events).

---

# S. Audit / Traceability Requirements

Every certification action must satisfy `CLAUDE.md` Rule 6 and `POA-INTEGRITY-CONTROL-001` §M, applied here specifically: record which mission authorized the certification review, which evidence (§G) was considered, which authority (§I) granted or declined it, and which commit introduced the resulting Status-field change. A certification action without a citable authorizing source is not performed — it is held and reported as an ambiguity, per the same Control Law pattern already governing integrity corrections.

- Certify any existing artifact, including `POA-KER-001`, `POA-RSR-001`, `POA-EXB-001`, `ORC-001-GOV-001`, or any `ADR`, as a side effect of `ACS-001` being materialized.
- Promote `POA-STD-011` from Draft to any other status.
- Establish a POA Baseline (`GAP-006`).
- Resolve `GAP-001` (`POA-PRS-001` vs. repository identifier convention — remains HELD).

- Create `RM-001` or `CTR-001` as executable artifacts.
- Modify any application code under `30-Products/`.
- Modify `ROADMAP.md` or `CHANGELOG.md` (not authorized by this directive).
- Push any commit automatically.
